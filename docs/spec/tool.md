# The design system and its tool

Records the design system, tool inputs, outputs and design file, with their status and reasoning.

**Owner (2026-11-01):** Konzilo is a pre-prototype on the way to Blueprint; long term, Astro in front and WordPress or Sveltia CMS behind, switchable. The framework's foundations are the plates (plates.md) and the page, header and footer models (page.md, header.md and footer.md); two things remain, the components and a tool. The design system must serve any site, also one someone else implements in WordPress or elsewhere from it.

*Decided* 2026-11-01:

1. **A stand-alone design system**, its own repository with the tool, apart from the Konzilo core: download it, run it, tune colours and type, send the client the presentation, adjust, and export. Konzilo sites consume it; how is the assistant's proposal (below). Each site holds only its inputs and the components only it needs; Konzilo's plan, which gives each site its own design and components, changes by an ADR there. The generic decisions in this file move to the design system's repository.

   **One tool:** `konzilo-design tool <design-file>` opens the local editor, on the named file, or on a new design created there if the file does not exist; without a file it stops and shows its usage, and the first write of a run first copies an existing file to `<name>.bak.json` (*decided* by the owner, 2026-11-03). The command returns at once, and the tool runs like an application: each design file has a tool of its own, a file already open is shown in another window, the tool stops by itself 30 seconds after its last window closes, and a save made on a file changed since is refused (*decided* by the owner, 2026-11-11: the command returns at once, and New and Open inside the window are left out, since the command already opens any file; the rest is the assistant's design after a second opinion, in `tool/README.md`). It shows the presentation's pages with their controls in place, beside a live preview of the real components at mobile and desktop width at once, in one window or two (*decided* by the owner, 2026-11-03, after trying sketches; the narrow type scale shows only on a phone and the wide one only on a desktop, so both ends must be visible while dragging). One to three colours, typefaces, type scale, shadows, frame, corners and density generate every token together. Save writes the complete design file; a button makes the presentation for people (point 4). See `tool/README.md`.
2. **Inputs:**
   - one to three brand colours, ranked primary, secondary, tertiary, and always a grey scale;
   - typefaces (*decided* 2026-11-02): one typeface throughout is the norm, as a rule a sans-serif and often Mona Sans, so the simple path must stay simple:
     - the main typeface, preselected Mona Sans, with the system sans-serif stack and typefaces of one's own as alternatives; with nothing chosen at all the library uses the system stack;
     - the monospace typeface, which always exists: in the library the system stack until someone deliberately chooses one, and in a new design Mona Sans Mono. Choosing labels in monospace picks Geist Mono if the system stack was selected;
     - exceptional first-heading choices stay in the same role list, without a separate tool or mode;
     - a heading typeface, following the main one unless set, for example a sans-serif above serif text, and a display typeface for large text, following the headings unless set. They are inputs because the presentation is made from the design file and typeface tuning has to know which typeface a style has;
     - **where a need lives** (owner): in the tool if that stays simple. If it gets too complex, the tool is simplified and the need stays in the design system. If that too gets too complex, it goes out to the CSS. The goal is a simple tool for choosing the arrangement of typefaces and each style's step, with everything on the type scale;
     - the tool's type section shows this as one row per role, each following another role until changed, with a named ratio at each breakpoint. The first heading now has optional `typefaces.heading-1` and `type.heading-1-color` inputs; the latter selects the checked text or accent role. Absolute step controls preserve every other style's step while storing the schema's relative steps;
     - **Built** (*decided* by the owner, 2026-11-03): the library ships 47 variable typefaces in `src/fonts/`, the owner's list in the owner's order: sans-serif, slab serif, serif, display and monospace, plus two partners for body text. `bin/design-fonts` holds the list and fetches each from its best source, which is the designers' own repository where that is better and a family download from Google Fonts where that is, never a font service's stripped web files. `catalog.js` is written from it, with each typeface's roles and its axes as read from the file. A display typeface is only for the first heading and larger. Each typeface has an italic of its own, drawn or sloped by its designers, or one reached through its slant axis; Roboto Slab and Mona Sans Mono have neither and stay upright, since a browser never synthesises one (`font-synthesis-style: none`). The presentation inlines only the typefaces a design uses. A site serves font files itself, without a third-party font request;
     - **Every role is set on its own** (*decided* by the owner, 2026-11-03): text, headings, the first heading, display, labels and code each choose a typeface and turn the axes that typeface has, with the letter spacing and its alternate letters (`typefaces.<role>`, `type.roles.<role>`). The first heading follows the headings or display text, the owner's reason being that it is special, and keeps its own size on the type scale. A new design uses Mona Sans for everything, with its own Mona Sans Mono for code, and sets two roles: display text light and open (weight 260, width 112, optical size 100, spacing -0.03) and labels with the look of Mona Sans Mono at width 75 and weight 800, but in the proportional Mona Sans, since a monospace forces every glyph to one width (weight 800, width 75, optical size 0, spacing 0.06, `ss02` for the slab I, `ss07` for the square G). An existing design without settings keeps its recipes;
   - the label style (*decided* 2026-11-02): labels in the main family, the default, in the monospace family, or since 2026-11-03 in a typeface of their own. components.md, Typefaces and labels, has what counts as a label and the recipes;
   - the body size, set as at the narrowest and widest window;
   - a type scale (ratio), and for each heading level how many steps it climbs from the one below, for a faster progression where wanted; not a switch between two scales (*decided* 2026-11-01):
     - The ratio, the base of the scale, is set at two breakpoints, like the body size, so headings close up on a phone and open out on a wide screen (*decided* by the owner, 2026-11-03; it replaces a straight line on each size in a fixed 320–1440px window, of 2026-11-01). A size is the body size times the base to the power of the style's step, so at every width the styles form a true scale. The base and the body size each follow a straight line between the breakpoints and stay fixed outside them: one scale with the same steps throughout. With one ratio everywhere, a display heading could be 55px on a phone; with 1.067 there and 1.125 on a wide screen it is 33px.
     - The breakpoints lie anywhere from 320 to 1920px with left at most right, 390 and 1440px by default (`type.breakpoints`). On one width the scale changes at once there, as at a media query's `min-width`.
     - In CSS each size is `calc(body * pow(base, step))`, in `@supports`, as `pow()` and `atan2()` give a window width as a number. A browser without them keeps a `clamp()` between the same two end values, with a straight line on the size. The two differ only between the breakpoints, by a pixel or two at ordinary settings.
     - The tool shows this as a number line (*decided* by the owner, 2026-11-03): at each breakpoint a filled arrow to drag, with the width under the line and above it the base and the name of its scale. The figures can be typed over, the name opens a menu of the named scales and says Custom off them. A hollow arrow under the line says which width the rows below show, and changes nothing in the design.
     - Steps: h6 from body text, then h5, h4, h3, h2, h1 and display each from the level below; the lead above body text; small text below it, and labels below body text as well. The default: 0, 1, 1, 1, 1, 3, 3; lead 1; small text 2 below; labels 3 below (5 until the owner asked for eyebrows a step larger, 2026-11-12; components.md).
   - shadows, from none through barely visible and very diffuse to a hard, solid outline (*decided* 2026-11-01, after the owner tried a live model of it):
     - Each elevation has a tuned shape, a near and a far shadow, inked with the shadow colour: the header over the page, the header over an open panel, a panel over the page, the page over the footer, a box, and a lifted box at twice the box's elevation.
     - Four sliders transform every elevation alike, each mapping straight onto `box-shadow` values: strength scales the opacity, and zero is off, with no switch of its own beside it, since no target casting a shadow comes to the same (owner, 2026-11-03); elevation scales distance, blur and spread; the light's angle turns the offset; hardness below its reference position widens blur and spread up to double, and above it shrinks them to zero. At hardness 100 the shadow is a solid offset in the full shadow colour whatever the strength (the owner's expectation, for designs like the Tove and Oaknut WordPress themes). Hard shadows round to whole pixels.
     - The reference positions are strength 50, hardness 20, angle 0 and elevation 50, and there each elevation is its tuned shape unchanged. A new design starts from the owner's defaults (2026-11-03): strength 0, hardness 30, elevation 50, falling straight down, in the text colour, with every target casting a shadow. The strength slider catches at 50.
     - The shadow colour is the text colour by default, or one of the brand colours, grey or black.
     - On a dark plate a shadow stays dark (*decided* 2026-11-01, after comparing it with the plate's light text colour and with a hairline): where the default text colour would be light, the shadow is black at three times the opacity. A light shadow there is only a faint glow, and a hard light offset merges with a white card. On a near-black plate even this fades, and the card shows because a raised plate is lighter than its ground. A shadow colour chosen explicitly is used as chosen.
     - Where shadows fall is chosen per target: cards (later other raised components), the header, the megamenu, the page over the footer. A hard shadow suits cards, not the large layers (owner). A layer without a shadow is set off by the hairline, as at strength zero.
     - Off by default; switching on starts from the reference positions.
   - a frame, a setting of its own apart from the shadow (*decided* 2026-11-01): thickness 0–3px, none by default, and a colour, the shadow's by default; always solid, its corners from the corner slider. The owner found a 1px frame heavy (2026-11-11); it is the colour, the text's at full strength, not the width. So the colour has one more choice, Quiet edge (`border`), each plate's own `border` role, following its Surface and the mode, and a filled button's ring its own hover fill (generator.md, Shadows and frame); the width keeps whole pixels. Which components take it is settled with the components. The thin grey lines of tables and fields are colour roles, not this;
   - one corner slider, from square through almost square (a few pixels) and discreet to clearly rounded;
   - one density slider, from very compact to very loose, with the default towards the looser side.
   - the frame (*built* on the owner's word, 2026-11-03): what surrounds every page is chosen in the design too, in `header`, `footer`, `page`, `breadcrumbs` and `layout`. It starts with the header, the footer and the page, and then come the components that can stand on a page. Of those the hero is chosen too, in `hero` (owner, 2026-11-04): the page has one hero and the choices of size, picture, the text's place up and down and across, colour or overlay and heading (owner, 2026-11-05, in that order), rather than a sample of each combination, and the presentation and the sample page show that one. The heading has two settings of its own, where the page's H1 is and how the hero's heading looks, in all four combinations (owner, 2026-11-05; components.md, The H1, the trail and the hero's heading). No choice is disabled: one with no effect in a combination simply has none. The footer's cells are chosen on a miniature of its two bands, one click per cell (owner, 2026-11-05). The footer's attachment says what it is fixed to, the end of the page or the bottom of the window, and beside it stands where the page meets the footer, the page's shadow on it and the line at its edge, which the design file keeps in `page` but which concern only the footer, so the Page page keeps the widths and the page's surface (*decided* by the owner, 2026-11-11; footer.md, Attachment). header.md, footer.md and page.md say what each setting means. They pass unchanged to `resolved`, for a site to give to its Header, Footer and Page, and they emit no CSS except the widths.
   Type and space are always fluid; everything else follows from the inputs.
3. **Lengths** (the owner asked the assistant to settle it, and approved its proposal on 2026-11-01). A visitor who raises the browser's text size, instead of zooming, keeps that choice only where lengths are in rem or em; zoom works with any unit.
   - The root gets no font size, not even in pixels, so the browser's setting holds. For nearly every visitor that is 16px, so nothing changes for them.
   - rem for type sizes, space, widths, radii and breakpoints.
   - Fluid values as `clamp(min, rem + vw, max)`. Space and margins run between windows of 20rem and 90rem, 320px and 1440px at the default setting; type sizes between the design's breakpoints, in `calc()` where a browser can (point 2, type scale).
   - em inside components, for parts that follow their own text: a button's padding, an icon beside text.
   - px only for what is drawn rather than read: hairlines (1px), the frame (0–3px), focus rings (2px) and shadows. The header's T (24px) is a scroll distance, not a CSS length.
   - line-height unitless, letter-spacing in em.
   - The tool, the design file's `inputs` and the presentation speak in pixels at the default setting, as people think; the generated CSS writes rem, so 17–19px between those windows becomes `clamp(1.0625rem, 1.0268rem + 0.1786vw, 1.1875rem)`.
   - This covers the tool's own interface, the report and the gallery too, not only the components (owner, 2026-11-05): their stylesheets, media and container queries, inline styles and lengths written by scripts are in rem. A number shown to people, such as "17 px", is a word and stays. Beyond what is drawn, px stays only where a value truly is a device pixel measure: a preview frame that simulates a real window width (390, 1440), geometry measured at runtime and written back (drag positions, the divider, the number line's arrows), the scroll distance. Gaps, paddings and sizes of 1–3px that are not lines are in rem like any other. `DESIGN.md` writes its dimension tokens in rem, which its format accepts.
   - `test/lengths.test.js` holds this: it fails on a px length that its one short list of exceptions, each with its reason, does not allow.
4. **Two outputs:**
   - **For people** (*decided* by the owner, 2026-11-02, replacing a PDF, because a PDF renders shadows and the like badly and leaves little room to explain): the tool writes a ZIP archive holding one self-contained HTML file that opens in any browser, with nothing fetched from elsewhere, and is browsed page by page.
     - **Progressive disclosure:** one page at a time. Colour first: the scale and its shades, then the colours on one another, light text on dark and the reverse, with the contrast ratios in fine print under each example instead of a large table. Typography next: the main typeface, the type scale and how it closes up and opens out with the window, the complementary typefaces, and examples in use. Then space, corners and shadow.
     - **Components by theme:** header, footer, the page itself, then what goes on a page. A sensible selection is shown, not every combination, with the option to click for more variants. They are real and work as on a site.
     - **Details last:** whatever specific data remains comes at the very end.
     - **Written motivation:** per chapter, not per detail, the tool takes a text saying why a choice was made, for example why a typeface was chosen. It is shown on its first applicable page and kept in the design file's `project`. The typeface and type-scale pages have separate explanations; space and shape share one, while shadow has its own.
     - **Comments:** the reader can leave comments as they go. They are kept in the browser and leave as plain text, by mail or as a file, so the owner can read what the client thinks. No server is involved.
   - **For code:** the components, HTML and CSS, all of them with all their CSS, in a form a Konzilo site takes in simply and gets exactly what was decided.
   - **For AI agents** (*decided* by the owner, 2026-11-03): `DESIGN.md`, Google Labs' open format, still an alpha, with the tokens, the Surfaces, the components and the rules, so an agent can design pages from the same decisions. **Its reader** (*decided* by the owner, 2026-11-10): an AI agent with nothing but this file, building with any technique, a static site, a WordPress theme or anything else, not necessarily for Konzilo; so it must stand on its own, and what an agent cannot build from it alone is a gap in it. The design file is for Konzilo. **What it carries** (the assistant's choices, 2026-11-10, after an agent built a site from it alone and another compared that with one built from the package): every Surface in both modes, the picture Surfaces with their scrim and the status Surfaces among them; the name, the slogan and the logos, a logo as SVG text in a fenced block when it is an SVG of at most 24,000 characters, and otherwise named as missing, so an agent asks rather than draws one; type steps, sizes as CSS and the windows where features switch on; space, side margin and widths as CSS; every shadow with its use and its dark-mode value; motion; and each component's look as a recipe on roles, type styles and space, kept at the level of the recipe so a small CSS fix does not make it false. It names no `--kn-` variable or `kn-` class, since no stylesheet comes with it. **Light and dark mode** (*decided* by the owner, 2026-11-10): DESIGN.md describes the two modes as two equal sets and decides nothing about using them; whoever consumes it chooses light only, dark only or both, and if both, how a visitor gets each, so it neither tells an agent to follow `prefers-color-scheme` nor to offer a switch. The second round of the blind build (the assistant's choices, the same day): the frame's width and colour, or that a design has none; the status roles of every Surface; the icons each component uses, with direct downloads; a direct download for each typeface, Google Fonts' faces from Google's font repository; and a fallback where a recipe uses CSS a current browser lacks. **The export is a ZIP** (*decided* by the owner, 2026-11-10, since that is much easier for a receiver; the name and the split by extension are the assistant's choices): `<name>-design-md.zip` beside `<name>.design.json`, holding DESIGN.md and what it names by relative path, the logos, the font files of the design's typefaces with their licences and `@font-face` rules, and the icons the components use with their licences, all from the design file and the repository, so it works offline. `-o` with `.md` writes DESIGN.md alone, which then links to downloads and asks for a logo it cannot carry. Neither replaces a file it did not write: DESIGN.md carries the marker in its text and the archive in its comment. The format's own command turns it into DTCG tokens or a Tailwind theme, so those need no export of their own here.
5. **The design file** (owner's idea; the assistant decided its form, 2026-11-01): the tool's settings produce one JSON file, the source, which is what is handed on; everything else is made from it.
   - `format`: a required whole number saying how to read the file, raised only when its shape breaks (*decided* by the owner, 2026-11-05; konzilo.md, The three versions).
   - `inputs`: what the tool's controls set, the only part a person changes, through the tool.
   - `project`: the presentation name, optional string `version` (default `1.0`), `logo` and optional `logo-dark`, as data URIs or paths relative to the design file. The document version is independent of the generator version. Since 2026-11-11 also the client's own `menu` and `footer`, content for the preview and the presentation, not design (The client's own menu and footer, below).
   - `resolved`: every value the generator derived (ramps, each plate kind's roles in light and dark mode, type and space steps as min and max, radii, shadows as finished CSS values), with the generator's version, a fingerprint of `inputs` and the contrast check's result.
   - Consumers read `resolved` and need no generator, so a consumer in another language (a future WordPress plugin setting a theme's values) never reimplements the colour maths, and every consumer gets the same values. A file whose `inputs` no longer match the fingerprint is refused. Consumers: the Konzilo package, the presentation, the export, later others. Its own plain format; DESIGN.md (point 4) is how it reaches other tools.
6. **Where:** the repository `Kntnt/konzilo-design` (private, created 2026-11-01), locally `~/Projects/konzilo-design`; Konzilo sites take it as a tarball in their repository, with the fonts a design uses copied beside its file and the design file itself, read by `fromDesign` in their `astro.config.mjs`, and others take the export (*decided* by the owner, 2026-11-05; konzilo.md has the contract and a how-to).

## HTML presentation implementation (2026-11-02)

The local button is **Create presentation**; it saves before packaging. The CLI
`konzilo-design presentation <design-file> [-o out.zip]` resolves without changing
the source. The former PDF command and renderer are removed. The default ZIP is
`<stem>-presentation-<YYYY-MM-DD>.zip`, beside the source, stripping `.design`.
It contains only `<project-name-slug>-<document.filename>.html`; the final filename
word is a copy key. All assets are inline and the build needs no browser.

The reader has 23 pages: Start, two colour pages, four typography pages, three
space/shape pages, eleven component pages, Details and Comments. Hash routing
preserves history. The desktop sidebar is 260 px; a menu replaces it below 900 px.
The actual component specimens load lazily in independent real-width iframes.
Shared CSS, fonts and scripts are held once and inserted at runtime. The full-page
specimen scrolls in a 560 px viewport; ordinary specimens fit their content at
every width, and the content below follows when their width or mode changes.
At Tablet and Phone the bordered screen hugs the frame, with only the document
around it. Reference data and additional variants are disclosed on request.

Optional project fields are `introduction`, `contact: { name, email }` and
`explanations: { colour, typefaces, type-scale, space-shape, shadow, components }`,
and since 2026-11-11 `menu` and `footer` (below).
They never enter the input fingerprint. Plain text is escaped; blank lines make
paragraphs. The first page for each explanation is respectively colour scale,
main typeface, type scale, space, shadow and header. Introduction and contact
controls are on the tool's Start page. Explanation controls finish their relevant
page, after its controls and examples.

Comments, edits, reader name and drafts save as typed in browser localStorage,
keyed by document identity and version. Inaccessible storage uses memory with a
visible reminder. Export includes unsent drafts as readable UTF-8 plain text.
Mail links above 1800 encoded characters use a short attachment note. Comments
remain after export and are cleared only by an explicit confirmed action.
The content security policy refuses network access, including third-party media;
its local explanation remains interactive. See `presentation/README.md` for the
copy override, offline asset and verification contracts.

## History (2026-11-05)

The owner asked for history with undo and redo. Every change autosaves straight into the design file and the run's backup holds only how it began, so without this a slip of a control overwrites the earlier value for good.

History covers what is saved in `inputs` and `project`, whichever control changed it, in steps of one gesture each: a drag, a key held on a slider, a burst of typing, a click. It lives in the window's memory, at most 200 steps, and a reloaded window starts empty. An undo or redo goes to the page of the change and to where it was scrolled, also on the page already shown, because a change out of sight confuses. The ways of looking at the design are not in it, and neither are a client's own photos: they are files beside the design file, and keeping what Remove deleted would need a store of its own. See `tool/README.md`.

## One component once (2026-11-05, *replaced* 2026-11-11)

The owner had decided that each component appears once in the tool's preview, and that its variations are reached by choices in the left panel, as the hero and the footer already worked. His decision of 2026-11-11, below, replaces it.

## The panel holds only what is saved, and the preview every variant (2026-11-11)

The owner decided that the tool's control panel holds only what the design file saves, in `inputs` and `project`, and that the preview shows every variant of a component at once instead of a choice on the left. It reverses his decision of 2026-11-05, for his reason: "The biggest and most confusing shortcoming is which controls actually affect the design system and which only change what I see in the preview. [...] Simply: what is in the control panel should only be about what actually has an effect." Choices that looked like settings and saved nothing, such as a Callout's status or the picture's side in Text and Image, left him unsure what he was setting, and a choice common to the whole site meant nothing for what a site varies from one use to the next.

- **On the left, only what is saved.** The component pages' rows of looks and the Header page's two "Show it in the preview" buttons are gone. The ways of looking at the whole preview stay in its own bar: Light and Dark, Mobile and Desktop, Pictures and None, the desktop's width and scale.
- **Variations come in two kinds.** Those stored in the design file (hero, footer, header, breadcrumbs, and since 2026-11-12 where the line across the tabs stands, on the Text page, whose preview shows tabs over values for it; components.md, The owner's review of a site built with the components) are set on the left. The rest are chosen per use by whoever builds a page, such as a Callout's status, a Button's kind, a Card's plate or the picture's side in Text and Image. These are not design settings, and the schema has none for components; the preview shows them all at once, each named by a short caption, such as "Warning · Outlined". Interaction states stand side by side, and a component that a site sets on other Surfaces stands on each. Every value of every dimension shows at least once; dimensions are combined where that stays small, and a compact grid names its rows and columns where every combination would be too many (the assistant's selection, in `tool/README.md`). A real multiple, such as a Card Grid of several cards, is its own component and not a variation of Card.
- **Each component page has a preview of its own**, with its own components and nothing of the next page's, in sections named as the page lists them. A page with nothing to set says that the preview shows each component with its variants, and that a site chooses among them per use.
- **The hero keeps its settings**, the one component with settings of its own: the opening every page gets, unless the page itself chooses otherwise.
- **The Header page shows the large menu and the search box open**, each in a frame of its own under the page, at both ends, following every setting; no click opens them.
- **Accordion and Quotation are two components**, each with its own specimen, and the accordion shows three questions. The report keeps its pages, its specimens behind their disclosures and its side-by-side variants, and only these specimen fixes reach it. See `tool/README.md`.

## The colours together, where the colours are set (2026-11-11)

The owner asked whether the examples on the tool's second colour page, text, links and buttons on every Surface with their contrast, would not be more natural on the page where the colours are changed, and decided so. In the tool they now stand on the colour scale page, after the colours and before the explanation, so a change shows at once, and the separate page is gone. Where the document is wide, as with the preview in its own window, they stand beside the colours instead (the assistant's choice). The report keeps its two colour pages, since a client changes nothing there and is led through one thing at a time (point 4; the assistant's reading of the request, which was about the tool). See `tool/README.md`.

## The page's H1 (2026-11-05)

The owner decided that a page's first heading is always its H1, with the trail directly before it, and that the H1 can stand in the hero or under it (components.md, The H1, the trail and the hero's heading). The Hero page has the choice beside the heading's look, in short words, and neither limits the other. The preview changes in place, without a build: the heading's element changes tag and the trail moves, in the same frame, so nothing flickers and nothing on the left moves. The trail has no setting for its place, so the Breadcrumbs page only says where it stands. The sample page opens with one Hero, followed by a plain Band whose heading is the `<h1>` or the `<h2>`, exactly one `<h1>` whichever the setting. The second Hero it used to have is gone, as it was only a variation, so display text has a heading further down the page of its own, which keeps the Display role's controls in the preview whatever the hero's heading looks like (the assistant's choice).

## Sample pictures (2026-11-04)

The sample pages show real photos, because a client judges a hero or a card by how it looks with a photograph in it. They are a small neutral set in `presentation/pictures/`, without recognisable faces or legible brands; people stay drawn, in the design's colour. A client's own photos take their places as files in a folder beside the design file, and are embedded only when a presentation is built. They stay out of the design file, because the tool sends the model to the preview on every step of a drag, and out of this repository. Whether the pages show pictures is a way of looking at them, in the tool and in the presentation alike, not a design setting.

## The client's own menu and footer (2026-11-11)

The owner asked that, just as a logo and pictures give the client's own look, the menu and every footer cell can show the client's own content, since with generic content the client asks "but this is not what we agreed" and has to be told to look at the design instead. He accepted, before it was built: the fields stand on the Start page, beside the logo and the pictures; the menu is an indented list in one text field, a line set in under another its child, the large menu's headings the top level and its links the next, and a dash before an item's short description, as in `Compact series - For where space is short`, with a syntax that takes a pasted outline or site map, told in the field's tooltip and shown by a placeholder; the footer has a field for each cell, in the order and with the names of the Footer page's miniature, in a plain format for each kind of cell; the content is kept in the design file's `project`, like the introduction and the contact, so it is in the history and saved with the design, structured rather than as raw text unless there is a strong reason, with the schema backward compatible; it is no design, and changes no input, fingerprint, CSS or what a Konzilo site gets; wherever the preview and the presentation show the sample menu or footer, the client's content takes its place, cell by cell, an empty cell keeping the sample and its field saying so, and the preview follows typing.

***Built* the same day; the assistant's choices:**

- **The outline.** One item a line. A line's level is where its words begin, so spaces, tabs (to stops of four), bullets (`-`, `*`, `•`, `o` and their kin), numbers (`1.`, `1.2`, `a)`) and a drawn tree's lines (`├──`, `|--`) all set it in, a line set in further than the one above it is its child, and one set in less goes back to the line it lines up with. So a document's bullets, Word's plain text, Markdown, a numbered outline and a terminal's tree read alike, and a heading with bulleted lines under it reads as it is written. The first dash, hyphen, en or em dash, with a space on each side begins the description, so `Spare-parts` stays one word. Blank lines count for nothing. A browser's plain text of a list copied from a page or a document may have lost its levels, so a paste with a list in its HTML is taken from that: nested lists, a Google Docs list's `aria-level`, Word's `mso-list` levels, and headings over lists, as a site's large menu has them. It is written back two spaces a level, which reads again as it was.
- **The footer's formats.** Links take one link a line, by their words, and a row pasted as one line parts at a bullet or a bar. Text keeps its lines, each a line in the cell. Networks take one a line, matched in any case to the library's icons, LinkedIn, Facebook, Instagram, YouTube, X, Spotify, Email and RSS, also by another name (Twitter, E-mail, E-post) or an address on the network, an email address or a feed, since a client's site is where they are copied from; any other name is kept and shows as a word among the icons, rather than vanishing. The upper band's A1, the brand, has no field: the identity already gives it, and the field's place says so. The upper band's B2 without links of its own is the top level of the menu shown, the client's once there is one, as the sample's is the sample menu's, so a client's menu never sits over the sample's links.
- **Stored structured.** `project.menu` is a tree of `{ label, description, items }`, and `project.footer` holds `upper.b1`, `a2` and `b2` and `lower.a1`, `b1`, `a2` and `b2`, lists of words or a text. Structured, because the presentation's build and the preview read it without the tool's parser, and the schema can check it; a field shows the words for what is kept, and while it is in use it keeps the words as typed if they come to the same, so the caret and the browser's own text undo stay. What is emptied leaves the file, with any group it empties, so a design without the content has none, as a file from before.
- **The link menu** takes every top item, as on a Konzilo site by default; the header gives way where they do not fit. An item below the second level follows its own in order, since Header's children are one level, as `menuProps` does with a site's menu.
- **The preview.** The Start page shows the large menu open under the page, as the Header page does, and a field in use takes the page to its top for the menu and to its end for the footer. A modal dialog opened in a frame took the focus from the tool, and keys typed meanwhile were lost, so the frame opens it while it is inert.
