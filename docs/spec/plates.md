# Tokens, roles and plates

Records the token, role and plate model, its decisions and open questions.

**Owner (2026-10-31, night):** the page, the header and the footer are the start of a component framework; cards, forms, buttons and the rest follow. All of them use colours in roles, and spacing, shadows, radii and type likewise. He sees three levels: a framework of **tokens** (colours, radii, spacing, font sizes), a level that maps them to what he calls **roles**, and **components** that use only roles, so that changing the brand colour or the type size carries through to every component and still looks sensible. He recalls Material 3 and his own idea of **plates**: text placed on a colour plate says by role that it is text on that plate, and turns light on a dark plate and dark on a light one by itself. He recalled that the assistant once found Google's solution flawed and had a better one. He asked for research and an idea to present on 2026-11-01; components come only after he has settled the idea.

**Research** found the earlier idea: Blueprint's accepted Surface contract (Q314, 2026-09-14: a Surface supplies a complete set of context roles to its subtree, "no `on-` colour pairs exist anywhere") and ADR 0026 (palettes generated at authoring time in OKLCH against contrast targets). The original criticism of Material itself was not recovered. The research surveys DTCG, Material 3, Radix, Carbon, Primer, Polaris, Atlassian, Spectrum/Leonardo, Open Props, Tailwind v4, Lumos, Utopia and Apple. It compares on-pairs with inherited plate contexts and gives 2026 browser support.

***Decided*** 2026-11-01: the owner accepted this proposal and the six recommendations below. Stance: keep his three levels, split the middle one into context roles that a plate supplies and global roles, generate and check colours when the design is set, not in the browser. This is Blueprint's Surface model carried into the new component model, under his word "plate".

1. **Inputs.** The few choices a site makes: brand colours (seeds), grey temperature, typefaces, base font size and ratio at the narrowest and widest window, density, corner profile, depth profile. Everything else follows from them.
2. **Tokens** (values), computed from the inputs: colour ramps (OKLCH, 100–900, solved for contrast); fluid type steps; fluid space steps; radii; the one layer shadow and a card shadow; durations and easing; the layout values Wide, side margin, the measure (Narrow) and the Aside minimum. Components never read tokens.
3. **Roles.**
   - **Context roles**, supplied by the plate underneath: `--background`, `--text`, `--text-muted`, `--border`, `--border-strong`, `--link`, `--accent`, `--focus`, `--success`, `--warning`, `--error` (Blueprint's ten plus an accent), and a polarity marker, light or dark.
   - **Global roles**, the same everywhere: type (body, small, lead, eyebrow, the heading sizes apart from heading levels, display, mono), space (gap inside a component, column gap, band space, the smaller gap in a run of same-coloured bands), shape (control and card radius), depth (the layer shadow), layout (Wide, side margin, Narrow, Aside minimum).
4. **Plates.** Anything that paints its own opaque background is a plate: the page, a band, the header bar, a footer band, a card, a button, the megamenu, the search box. A plate takes one **plate kind**, which sets its background and the complete set of context roles for everything on it. Text on a plate uses `--text`; it is light on a dark plate and dark on a light one without anyone saying so. Content that paints no background inherits; a plate inside a plate starts a new context (a light card in a dark band).
   - Kinds: `page`, `raised` (a card on the page), `tint` (light brand tint), `brand` (dark brand), `inverse` (dark neutral), `accent` (the brand fill, for buttons and small marks), `picture-light` and `picture-dark` (an image with a tested overlay or text plate).
   - Each kind has values for light and dark mode, both set by the generator (page.md, point 1). Some kinds stay dark in both modes (brand, inverse); others follow the mode (page, raised, tint). A plate may set an explicit local mode, as the light card in the reference implementation does.
   - The polarity marker feeds the header (transparent over the first band, it takes the band's polarity, now with no separate declaration), one-colour logos (`currentColor`) and `color-scheme`, so browser controls and scrollbars match the plate.
5. **Why not Material's on-pairs.** Material pairs every fill with an on-colour (primary / on-primary). Every piece of text must then know what it stands on and pick the matching on-role; nesting, images and brand colours of middle lightness break it, and the pairs multiply with states. A plate keeps Material's discipline, each kind being a validated pairing, but delivers it as context, so components do not choose. A button is a small accent plate.
6. **Generated and checked, not computed live.** When a brand colour changes, the token tool regenerates the ramps in OKLCH against contrast targets, resolves every plate kind, checks a matrix (each plate against text, muted text, links, needed borders, focus and states) against WCAG 2.2, and refuses a set that fails. The CSS holds literal values. Live derivation in CSS (Lumos's `color-mix`, `contrast-color()`) cannot promise contrast; `contrast-color()`, cross-browser since April 2026, gives only black or white.
7. **CSS mechanics.** A plate kind is a class or attribute that redeclares the context roles, which works in every browser; nothing depends on style queries or `if()`. Each plate also sets `color-scheme`.
8. **Propagation.** Brand colour → ramps → plate kinds → every component. Base size or ratio → type steps → type roles. Density → space steps → space roles. Corner profile → radii. No component changes.
9. **Component tokens** only where a component has a genuinely independent decision; most have none.
10. **Lumos and Blueprint.** Lumos for Astro uses the same mechanism (theme classes); the mechanism is a plain CSS pattern, and the design system has no ties to Lumos (principles.md, *decided* 2026-11-01; Blueprint's Q367), with generated values in place of Lumos's live derivations. Blueprint calls a plate a Surface (Q314, Q370); reuse that English name, with *platta* in Swedish.

**Presented** in the reference implementation (Swedish, with a live demonstration: brand colour, mode, type, density and corners driving the plates, and a contrast table). In it a yellow brand turns the dark brand plate olive in dark mode, the known yellow-to-brown effect; worth raising with the plate kinds.

**Decided with the owner** (2026-11-01, all six as recommended in the presentation):

1. **Plate kinds:** `page`, `raised`, `tint`, `brand`, `inverse`, `accent`, `picture-light`, `picture-dark`. Content without its own background inherits and needs no kind.
2. **Dark mode:** `brand` and `inverse` stay dark in both modes; `page`, `raised` and `tint` follow the mode; a plate may set an explicit local mode.
3. **Generated, not live:** colours are generated and checked in the design tool, the CSS holds literal values, and the export stops on a failure. Fluid type and space stay explicit CSS relations.
4. **Context roles:** the eleven in plates.md, point 3 (Roles) plus the polarity. Hover, active and other states get checked values when the components are defined.
5. **Names:** *platta* and *plattsort* in Swedish, Surface in English. The role names here were working names; the name list in names.md settled them on 2026-11-01, with the prefix `kn-`.
6. **Source:** the token tool sets the inputs and runs the generator; its JSON state is the source and CSS the output. A DTCG export only when something needs it.

**Still open:** a yellow brand's dark plate turns olive in dark mode, for the generator to solve; the components, which the owner defines next.
