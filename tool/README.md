read when running or changing the local design tool, its controls, persistence or presentation command

# Design tool

Run `bin/design-tool path/to/name.design.json`. A file that exists is opened as it is, and a file that does not exist is created as a new design. Without a file the command stops and shows its usage; nothing is remembered between runs. Opening a file never writes to it. A file with no format number opens as it is and gets one at its next save, and one with a newer number than this version reads is refused (`docs/spec/konzilo.md`, The three versions). Every change is saved at once, and the first write of a run first copies the file to `name.design.bak.json`, replacing the backup of any earlier run; a save that would change nothing writes nothing. `bin/design-restore path/to/name.design.json` puts the backup back, after asking.

The other commands take the file the same way: `bin/design-presentation` makes the presentation and `bin/design-check` checks the file. `bin/design-gallery` and `bin/design-test` build the gallery and run the tests. Each runs from any folder. `bin/design-tool` also takes `--port 4174` or `--no-open`, as does `npm run tool -- path/to/name.design.json`. The dependency-free Node HTTP server binds only to `127.0.0.1`. The command prints its URL and the absolute design-file path, and stops with Ctrl-C. If the port is taken, it says so and starts nothing.

A new design (`new-design.js`) is deliberately plain, and deliberately in need of replacing: a made-up company, Placeholdr, with a made-up symbol for a logo, shown alone until someone turns the name on, Mona Sans for everything, its axes giving display text and labels each their own look, its own Mona Sans Mono for code, one blue-purple for everything, no shadows, no frame and square corners. The rest are the library's defaults. These are the starting point of the tool; `defaultInputs()` remains the generator's fallback for what a design file leaves out.

On the main typeface page each role, Text, Headings, First heading, Display, Labels and Code, chooses a typeface and turns what that typeface has: one slider per axis, the letter spacing, and its alternate letters. Sliders are written from the typeface's axes in `src/fonts/catalog.js` when the role or typeface changes, never during a drag; a slider's value goes back to the default when clicked, and it is underlined while set. A new typeface keeps only the settings it has axes for. Run `bin/design-fonts` to fetch the typefaces again: it holds the list and writes `src/fonts/`.

**Export for AI** writes `DESIGN.md` beside the design file, in Google Labs' open format for describing a design system to AI agents: exact tokens with prose on how to use them, the components and the rules. `bin/design-md path/to/name.design.json` does the same, with `-o out.md` for another path. A `DESIGN.md` it did not write is never replaced. The Start page's **Design brief** opens that file: who the site is for and how it should feel, which the format holds to matter more than the values. `src/design-md/` writes it, and `npx @google/design.md lint` checks it.

The tool is the presentation in edit mode. `pages.js` writes the document: the presentation's pages, in its words (`presentation/copy.json` and the design's sibling `<stem>.copy.json`), with each page's controls in place. Every page runs in the same order: heading, controls, examples, explanation, next page. Every control is written once and stays in the page, so changing a value never rebuilds what is being dragged. A fixed menu has the chapters, the saved status and Light/Dark, with the chapter's pages and **Create presentation** below them. It has one height on every page, with room for two lines of page links whether a chapter needs them or not, and a page link is as wide whether it is current or not, so a page's heading always stands in the same place.

Beside the document, `preview.js` shows the real sample page in two frames at their real widths, Mobile at 390 px and Desktop at 1440, 1024 or 768 px, because a narrow setting shows only on one and a wide setting only on the other. The sample page shows every typeface role, so each control has something to change: a first heading and code at the top, then the grey and tints, and display text further down, as well as at the top when the hero's heading looks like it. Each end shows its Display and Body sizes and how much of the last setting reaches it (`Follows 94 %`). The modes are Both, Mobile and Desktop; only Desktop is ever scaled, and its figure toggles real size. The ends scroll together section by section, the end of one being the end of the other, and turning a page of the document takes them to the part it decides.

The divider between controls and preview has one optimal position per mode, computed in `logic.js`: the controls get a comfortable measure and the preview the rest, up to real size. It catches within 18 px and shows it with a heavier grip; a double-click or Home returns to it, and it follows window and mode changes until dragged away. **Full window** lets the preview fill the window. **Own window** opens a real second window to put on another screen, kept in sync over a `BroadcastChannel`; its own controls reach the first window, and closing it brings the preview back.

The interface wears the design it edits: `style.css` uses the generated roles of the page Surface, so Light and Dark and the grey temperature reach every part of the window, and the document's samples use the real component CSS. The tool's own words, a page's lead among them, keep one fixed face and size, so nothing moves while a control is dragged, and a sample whose height depends on a setting has its room held for it, as the Space page's band and the typeface's specimen do. Every change is saved after a short pause, regenerating the complete design file; there is no Save button. A window reloaded or closed within the pause still saves the change: it goes on `pagehide` as a `keepalive` request, with the same token and checks as any save. Such a request may carry only 64 KiB, so a logo the server already holds stays behind as a mark and the server puts it back; only a large logo chosen within that very pause cannot go along. The server takes saves in the order they came and answers `/api/state` after them, so the reloaded window finds the change. Clicking a logo tile chooses an SVG or PNG; a removed logo gives way to the client name. Tooltips overlay the interface, work on keyboard focus and disappear while dragging.

**Undo** and **Redo** in the menu walk back and forth through every change to what the design file holds in `inputs` and `project`: every control on every page, the logos and the written text. One gesture is one step: a drag from pointer down to pointer up, an arrow key held on a slider until it comes up, typing until a second's pause or the field is left, and each click or choice on its own. A change that ends on the value it began from adds no step, and a new step clears what could be redone. The keys are Cmd or Ctrl+Z, Cmd or Ctrl+Shift+Z and Ctrl+Y, also with the focus in the preview or the preview's own window. In a text field they stay the browser's own, for the text. An undo or redo goes to the page of the change, scrolled as it was then, and on the typeface page to the role it was made on, since a change out of sight confuses. From there it takes the path of any change: the controls, the preview and the save all follow, and only what differs is written. Ways of looking stay out of it: page turns, Light and Dark, the preview's modes, Pictures and None, the components' variations, the width the type scale is shown at, the divider. A client's own photos stay out too, since they are files beside the design and a removed one is gone, and the tiles' tooltips say so.

`history.js` is the pure part: at most 200 steps, held for the window's life, in snapshots of `inputs` and `project` that share all that has not changed, so a logo is held once. A change only marks a step open, and the model is read when the step closes, so a drag pays nothing for it. `changed()` in `app.js` is the one hook: a control that goes through it is in the history by itself, and one that calls `sync()` and `scheduleSave()` on its own is not. A reloaded window starts with an empty history. A restarted server does not touch it: a window with the same file open keeps its work and its history, and one with another file open still refuses to save. A window on its way out has no time to ask a restarted server for its new token, so what it sends then is refused, whichever file is open.

A dragged control must not make anything flicker. Both ends take the newest design once a frame, and the sample page touches only what changed: a logo rebuilt blinks and moves the header, and an image set again is decoded again. The section in view stays where it is on the screen, whatever happens to the height above it, and transitions are off while a control moves, so each step shows at once. 

The colour sliders keep their own OKLCH values, so a colour outside the gamut cannot move them while they are dragged. The direction slider shows where the shadow falls and the arrow points there; the design file still stores the light's angle, its negative.

The chapters run Start, Colour, Typography, Shape, Frame and Components. Frame has a page each for the header, the footer, the page and the breadcrumbs, with drawings to choose a model from, toggles and lists. The trail's place is not among them: it stands directly above the page's H1. The header's Identity section has Brand, Slogan, Logo and name, and the slogan's place; none is ever disabled, and a setting with no effect in a combination simply has none. The brand reaches the footer too, and the footer's cell A1 changes where it stands, without a build. A logo that still shows is the same image afterwards, in the header and the footer alike, so it does not blink. The footer's main control is a miniature of its two bands: each of the eight cells is a button that turns the cell on or off and says which it is: one that is on is filled with its band's colour, and one that is off stands empty, and the page has no disabled controls. The preview changes where it stands (`presentation/src/frame-live.js`): an unchanged footer cell stays the same element, and a page scrolled to its end stays there as the footer's height changes. A button holds the menu or the search box open while it is set. Components has a page for each of the presentation's groups, and their preview is another page, `/catalogue.html`, with every real component. The first of them, the page's opening, instead sets the design's hero: one hero in the preview, on one made-up screen with the next section's real heading and grey bars for what follows it, which `presentation/src/hero-live.js` changes without a build. Its settings run as the owner listed them: size, picture, the text up and down and then across, colour and overlay, heading. The heading has two, side by side and free of each other: where the page's H1 is, in the hero or under it, and how the hero's heading looks, H1 or Display. The first swaps the elements in place, `<h1>` for a paragraph in the hero and `<h2>` for `<h1>` in the next section, and moves the trail, which `hero-live.js` always sets directly before the group that holds the H1; it does this on the sample page too, and takes the Breadcrumbs page's settings along, since the trail goes where the H1 goes. Colour and Overlay share one place, since only one of them can apply: Overlay shows with a picture behind the text, and Colour otherwise. Nothing on that page is ever disabled: a setting with no effect in a combination simply has none. The six pictures stand in two rows, one column per kind, and are logical in the design file, `start` and `end`, though the page says Left and Right.

**Each component appears once in the preview, and its variations are chosen on the left** (the owner's decision, 2026-11-05: a page shows different components, not variations of one, so a change happens in the one component instead of further down, as it already did for the hero and the footer). Those stored in the design file (hero, footer, header, breadcrumbs) stay as they are. The rest are chosen per use by whoever builds a page, such as a Callout's status or a Card's plate, so they are ways of looking and not settings: like Pictures and None they are not saved and not in the history, and they last while the window is open. A component with no variations has no control, and a real multiple, such as a Card Grid of cards or the list under Visitor Filters, is itself one component.

`presentation/src/looks.js` lists each page's components, their looks and the words and tooltips of their choices, and `pages.js` writes one labelled row of `.pick`s per look. A choice goes through `setUi()`, never `changed()` or `scheduleSave()`, and reaches the frames with every design. The catalogue renders each variation once, from the report's own specimens: a specimen that is one variation as a whole has its look in `looks.js`, and one that holds several side by side marks each with `data-look="key:value"`, and what only the report needs with `data-report-only`. `presentation/src/looks-live.js` shows the chosen one and brings a component out of view into view, each end on its own. Nothing is rebuilt, so nothing blinks, and the left panel's controls stay where they are. The report ignores the marks and keeps all its variants, side by side and behind their disclosures. `Card Grid`'s three columns are the one variation only the tool shows. A state is offered only where it has a look of its own, here and in the report: a Button has Hover, Focus and Active, a Link Hover and Focus, as a link in Body Text does, and a Field Focus and Disabled.

The type scale is set on a number line from 320 to 1920 px. Each breakpoint has a filled arrow to drag, its width under the line, and above it the base and the name of its scale: the figures can be typed over, the name opens a menu of the common named scales, from Minor second to Octave, and says Custom off them. A drag catches at common widths. The left arrow can reach the right one and no further, and on one width the way the pointer goes says which arrow it took. A hollow arrow says which width the rows below show. A name and a base stand centred over their arrow and a width under it; when two would touch, the arrow being moved has its own stop short, and the other's stay where they stand. Each row below has its own fixed height, tall enough for what a style reaches at a scale without the warning. A sample shows its true size at the shown width, and a larger one is clipped by its row rather than pushing the rows below, so nothing on the page moves whichever control is pressed or dragged. `logic.js` owns the line's reckoning, the divider's positions and conversion between absolute displayed steps and the schema's relative steps. Changing a style recalculates both adjacent relative differences, preserving every other style's absolute size. Neighbours may meet but never cross, and each relative difference stays in 0–12.

`server.js` owns validation, atomic saves, logo embedding and local endpoints. Saves regenerate the complete resolved result. A contrast failure keeps the last good preview, disables presentation creation and the export for AI, and is held back from the save; the controls on every page still show what the model holds, and a way of looking still reaches the preview. Presentation creation saves the displayed settings first and returns the full ZIP path. The browser link opens the generated file through the same local server.

The preview is compiled from real Astro components once at startup into a folder of its own under `node_modules/.cache/konzilo-tool-*`. It is rebuilt on the next start so changes to components are included. Browser imports expose only explicitly allowed generator files, the schema, package metadata and UI modules. Mutations require a same-origin session token and JSON; Host and Origin checks reject cross-origin access.

The Start page's pictures show what each place on the sample pages holds. Clicking one chooses the client's own photo: the browser makes it a JPEG of at most 2000 px, so a camera's file does not weigh down the presentation, and the tool keeps it as `<stem>.pictures/<place>.jpg` beside the design file, never in the design file. The folder is the whole record: a file put there by hand under a place's name, from `hero` to `person-4` (`PICTURE_SLOTS` in `presentation/src/samples.js`), counts too, as JPEG, PNG, WebP or AVIF. Remove deletes the file, and the sample takes the place again; the backup does not cover the folder. Until then the places hold the photos in `presentation/pictures/`, and people are drawn in the design's colour. **Pictures** and **None** in the preview's bar choose how the pages are looked at, not the design: without pictures, a hero stays at its chosen height, since the height is a design choice, so one with its picture behind stands as a plain plate; a card closes up around what is left; and a picture that is the component itself, as in a Figure, keeps an empty place. A video keeps its still.

The Start page also stores the optional introduction, contact name and email. Each relevant page ends with an optional explanation, shown to the client: colours, typefaces, type scale, space and shape, shadow and components. These are `project` metadata; they do not affect the input fingerprint. Textareas have fixed heights so dragging another control cannot change the page's geometry.

For scripts: `node bin/konzilo-design.js presentation examples/example.design.json -o presentation/dist/example-presentation.zip`. Without `-o`, output is beside the input as `<stem>-presentation-<YYYY-MM-DD>.zip`. It resolves inputs afresh without rewriting the source design file. The ZIP holds one self-contained HTML file. See [the presentation guide](../presentation/README.md) for browsing, copy overrides, comments and offline verification.

The build needs no browser. `playwright-core@1.64.1` is a development dependency for tests only, using the already installed Chromium revision 1248. No browser download runs. Integration tests close their browsers and local servers in `finally`; temporary presentation build directories are removed after packaging.
